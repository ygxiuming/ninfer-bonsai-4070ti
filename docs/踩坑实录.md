# 踩坑实录

> 全部为真实踩坑，按部署顺序排列。每条都有症状与处方。
> Windows 侧的坑（bat 中文码页、CUDA dll 探测、中文路径硬性报错）见官方交付包
> `docs/复现手册-排错篇.md`，此处只记 Linux 侧。

## 一、系统与编译

### 1.1 Linux 线强制 ffmpeg 开发库，且没有关闭开关

- **症状**：CMake 配置失败 `Package 'libswscale' not found ... required packages were not found`
- **真因**：`CMakeLists.txt` 在非 MSVC 分支 `pkg_check_modules(FFMPEG REQUIRED ...)`，
  与引擎是否用视觉无关
- **处方**：`sudo apt install -y libavformat-dev libavcodec-dev libavutil-dev \
  libswscale-dev libcurl4-openssl-dev pkg-config`（Ubuntu 26.04 实测
  ffmpeg 8.x：libavformat 62 / libavutil 60 / libswscale 9，满足 ≥60/≥58/≥7）

### 1.2 TMPDIR 在 tmpfs 上导致 nvcc 并发编译 GCC 段错误

- **症状**：`ninja -j$(nproc)` 编译 CUDA 时随机 `cc1plus` 段错误
- **真因**：`/tmp` 是 tmpfs，`-rdc=true` 多路 nvcc 并发把 tmpfs 打爆
- **处方**：`export TMPDIR=$PWD/tmp-nvcc && mkdir -p $TMPDIR`（官方 README 同款坑）

### 1.3 偶发 cc1plus ICE

- **症状**：`cc1plus: internal compiler error` 随机出现
- **处方**：直接重跑 ninja（增量，秒级续上）；反复出现则 `-j6` 降并发

### 1.4 构建目录里 cmake 路径失效

- **症状**：`ninja: rebuilding 'build.ninja': subcommand failed`，报 cmake 不存在
- **真因**：build/ 里缓存了旧 cmake 的绝对路径，而那个 venv 被删了
- **处方**：重建同路径环境（venv + pip install cmake），或删 build/ 重新 configure
  （会触发全量重编，~10 分钟）

### 1.5 编译产物与官方字节数校验

- 官方交付树编译 549/549 步；产物与官方 Windows exe 差 3KB 以内属正常
  （源码快照后又有前进）。**判"能用"不看哈希，看起服 + 答对 + PPL。**

## 二、模型获取与打包（路径 B）

### 2.1 下载渠道

- Qwen3.8-27B / DFlash2 / PrismML GGUF：**魔搭都有原生仓库或镜像**
  （`Qwen/Qwen3.8-27B`、`incoai/Qwen3.8-27B-DFlash2`、
  `prism-ml/Ternary-Bonsai-2-27B-gguf`），`modelscope download` 国内直连，
  无需 token。HF 侧可用 `HF_ENDPOINT=https://hf-mirror.com`。

### 2.2 模板转换 CUDA OOM（12GB 卡）

- **症状**：`torch.OutOfMemoryError: Tried to allocate 4.74 GiB`
- **真因**：groupwise-int 量化的中间张量（grouped abs/amax）单次要 4.7GB+，
  官方卡 32GB 没问题，12GB 卡放不下
- **处方**：`--device cpu`。**实测仅 131 秒**（比想象慢不了多少），
  内存峰值 3.7GB——但整个转换过程需要把 27B 分片读进内存，
  **32GB 物理内存要配 64GB swap**：

```bash
sudo fallocate -l 64G /swapfile-ninfer && sudo chmod 600 /swapfile-ninfer \
  && sudo mkswap /swapfile-ninfer && sudo swapon /swapfile-ninfer
```

### 2.3 pack.py 是 Windows 快照，两处要改

- `NINFER_ROOT = r"E:\ninfer\..."` → 改成你的引擎树路径
- verify 脚本同样有 Windows 硬编码路径（`sys.path.insert(r"E:\...")`），批量替换
- verify 还缺共享模块 `_ternary_ref.py`（作者未随包发布）：可以用 pack.py 自己的
  GGUF 解析器写一个只读适配层（`tensors[name] → (ne,type,off)` + `raw(name,rows)`）

### 2.4 打包判据（不要跳过）

- `pack.py check`：zero_share **必须精确等于 0.3278**（PQ2_0 理论零码占比），
  偏了就是载荷错位
- `check_assembly.py`：**15/15**。作者踩过的坑：行置换非双射时
  **所有体积/字节校验照常全绿**，症状是"通顺的胡话"——只有内容级判据能拦住
- GGUF 元数据自检：`block_size=1024`、`Σsign_widths=28672`、`weight_names=401`、
  `inverse=[token_embd.weight]`

## 三、运行期

### 3.1 ★ 必加 --no-prefix-reuse（上游 bug）

- **症状**：第一个请求正常，**第二个请求 HTTP 500**
  `candidate token ledger does not match prompt length`
- **真因**：前缀复用与投机解码候选账本冲突（交付源码树快照的 bug；
  官方二进制比快照新 3KB，应已修复）
- **处方**：服务端必加 `--no-prefix-reuse`。代价是没有前缀缓存
  （多轮对话的系统提示会重新预填——以 1800 t/s 的 prefill 尚可接受）

### 3.2 reasoning_effort 命名不兼容（OpenAI 客户端）

- **症状**：400 `reasoning effort 'high' is not supported by the loaded chat template`
- **真因**：模板只支持 **low/medium/xhigh**；OpenAI 系客户端（如 ZCode）默认发
  `high`
- **处方**（二选一）：客户端改发 medium；或给引擎打别名补丁
  （`translate.cpp`：minimal→Low，high/max→XHigh），重编即可
- 请求级字段：`"enable_thinking": true/false`、`"reasoning_effort": ...`、
  `"preserve_thinking": true`（保留思考原文）

### 3.3 MTP 窗口的三层限制（K=7 不可行）

| 层 | 位置 | 默认值 |
|---|---|---|
| 1 前端校验 | `speculative_options.h` | [1,5] |
| 2 解码帧域 | `round_state.h kMtpDecodeMaximumDrafts` | 5 |
| 3 **内核** | `mtp_prepare_next_round: T must be in [2,6]` | **硬限** |

- 前两层改常量可过，第三层 T=窗口+1≤6 是内核级校验 ⇒ **K=5 上限**
- dflash/dflash2 需要制品含 DFlash2 weight bundle（现制品都没有）⇒ 报
  `unsupported head profile` / `no DFlash2 weight bundle`

### 3.4 接受率远低于官方口径

- **现象**：官方 4080S 实测 5.48 tok/轮（81.75%），我们同制品同协议只有
  2.0~2.4 tok/轮（逐位置 51/27/15/9/3%）
- **真因**：官方二进制比交付源码快照**新 3KB**（草稿策略改进未开源）
- **现状**：decode 持平旧引擎（~84 t/s），但 **prefill +79%、TTFT −60%、
  上下文 112k** 的收益照拿；等新源码发布

### 3.5 显存

- **症状**：重启服务 FATAL `requires ... bytes, but only ... available`
- **真因**：旧实例显存未放完就抢跑
- **处方**：`pgrep -x ninfer-serve` 确认清干净、`nvidia-smi` 回落到桌面基线再启
- **注意**：`pkill -f ninfer-serve` 会匹配到自己脚本的命令行把脚本杀了 ⇒ 用
  `pgrep -x`（精确进程名）
- **注意**：`--kv-capacity` 必须 ≥ `--max-context`（引擎硬检查）；
  KVMem 解耦是另一条线（zatfung）的特性，本线没有

### 3.6 显示器接核显

- 独显跑桌面实测损失 ~10% 显存带宽（官方 README 同款结论）
- Intel UHD 770 核显完全够输出桌面；切换后独显省 ~1.1GB 显存 + 带宽全量可用
- 12GB 卡上这意味着：96k→112k 上下文、启动裕量从"临界"变"健康"

## 四、其他

- **路径**：Linux 编译运行建议纯 ASCII 路径（Windows exe 是硬性要求，
  中文路径直接 `系统找不到指定的路径` 或 json UTF-8 异常）
- **思考模式**：服务端 `--no-thinking` 只是默认值；请求级
  `"enable_thinking"` 可逐条覆盖。开思考后短 `max_tokens` 会被推理吃满
  （表现是 content 为空）——给足 max_tokens 或关思考
- **多路并发**：官方口径每加一路单路掉 ~28%；聚合吞吐仍线性（实测 4 路聚合 336 t/s）
- **磁盘**：路径 A 全程 ~20GB（源码树 280MB + 制品 7.7GB + 编译产物 ~2GB）；
  路径 B 中途峰值 ~150GB（底座 52 + 模板 20 + GGUF 7 + 制品们），完成后可清到 ~30GB
